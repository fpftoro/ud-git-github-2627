### Conceptos Clave a Introducir y Reforzar:

1.  **`git remote set-url`:** Cambia la URL a la que apunta un remoto ya existente (normalmente `origin`), sin necesidad de eliminarlo y volver a crearlo.
2.  **Historiales No Relacionados (*Unrelated Histories*):** Ocurre cuando dos repositorios tienen commits que no comparten ningún ancestro común. Git lo detecta y evita fusionarlos o sobrescribirlos sin tu confirmación explícita.
3.  **Push Rechazado (*non-fast-forward*):** Un `push` falla cuando el remoto contiene commits que tu copia local no tiene. Es una protección de Git para que no pierdas trabajo por error.
4.  **`git merge --allow-unrelated-histories`:** Permite fusionar de forma explícita dos historiales sin ancestro común, resolviendo a mano los conflictos que puedan aparecer.
5.  **`git push --force` / `--force-with-lease`:** Sobrescribe el contenido remoto con tu historial local. Es una operación **destructiva**: solo debe usarse cuando estás seguro de que lo que hay en el remoto no importa.

**Contexto:** este procedimiento reproduce exactamente lo que haréis en la **prueba práctica del examen**: se os entregará un repositorio con el enunciado del ejercicio, que deberéis clonar, resolver en local y, finalmente, subir a un repositorio de entrega distinto.

### Fase 1: Creación de los Dos Repositorios en GitHub

| **Paso** | **Descripción y Comandos**                                                                                                                                                                                                                                                   | **Concepto de Git**                                                                                             |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------ |
| **1.1**  | **Crea el repositorio que simula el ejercicio:** en tu cuenta personal de GitHub (**no** en el Classroom), crea un repositorio llamado `ejercicio-examen-simulacro`, marcando la opción de **inicializarlo con un `README.md`**. **Alternativa CLI:** `gh repo create ejercicio-examen-simulacro --public --add-readme`.                                                          | Simula el repositorio que el profesor os entregará el día del examen, ya con contenido.                             |
| **1.2**  | **Añade un enunciado simple** editando el `README.md` de ese repositorio (puedes hacerlo desde la propia web de GitHub): por ejemplo, "Ejercicio: crea un fichero `solucion.txt` con tu nombre".                                                                            | El repositorio del ejercicio representa el punto de partida, no vuestro trabajo.                                     |
| **1.3**  | **Crea el repositorio de entrega:** crea un segundo repositorio llamado `entrega-examen-simulacro`, marcando también la opción de **inicializarlo con un `README.md`** (con un contenido distinto, por ejemplo `# Entrega`). **Alternativa CLI:** `gh repo create entrega-examen-simulacro --public --add-readme`.                                                                | **Importante:** lo inicializamos con README a propósito, para reproducir el caso real de un repositorio de entrega que **no está vacío**. |

### Fase 2: Clonado y Resolución del Ejercicio

| **Paso** | **Descripción y Comandos**                                                                                                                     | **Concepto de Git**                                                                                  |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------- |
| **2.1**  | **Clona el repositorio del ejercicio:** `git clone <URL_de_ejercicio-examen-simulacro>` y entra en el directorio creado.                          | Obtienes una copia local completa, incluido el `README.md` inicial.                                       |
| **2.2**  | **Verifica el remoto actual:** `git remote -v`. Debe mostrar `origin` apuntando al repositorio del **ejercicio**.                                 | Tras un `clone`, Git configura automáticamente `origin` apuntando al repositorio de origen.               |
| **2.3**  | **Resuelve el ejercicio:** crea el fichero `solucion.txt` con tu nombre, tal y como pedía el enunciado del `README.md`.                           | Trabajo local que aún no está confirmado.                                                                 |
| **2.4**  | **Añade y confirma la solución:** `git add solucion.txt` y `git commit -m "feat: Solución del ejercicio de simulacro"`.                           | El commit queda en tu historial local, todavía **no** se ha subido a ningún sitio.                        |

### Fase 3: Cambio de Remoto y Entrega en el Repositorio Correcto

| **Paso** | **Descripción y Comandos**                                                                                                                                                                                                                                                                                                                                                          | **Concepto de Git**                                                                                                                                                                     |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **3.1**  | **Cambia la URL del remoto `origin`** para que apunte al repositorio de entrega: `git remote set-url origin <URL_de_entrega-examen-simulacro>`.                                                                                                                                                                                                                                     | El nombre del remoto (`origin`) no cambia, pero ahora apunta a un repositorio distinto. **No** has vuelto a clonar nada.                                                                    |
| **3.2**  | **Verifica el cambio:** `git remote -v`. Ahora `origin` debe apuntar al repositorio de **entrega**, no al del ejercicio.                                                                                                                                                                                                                                                             | Confirma siempre el remoto antes de un `push` de entrega: es el error más habitual y más grave en el examen.                                                                                |
| **3.3**  | **Intenta subir tu solución:** `git push origin main`. **El push será rechazado.** Verás un error similar a:<br>`! [rejected] main -> main (fetch first)`<br>`error: failed to push some refs to '...'`<br>`hint: Updates were rejected because the remote contains work that you do not have locally.`                                                                          | El repositorio de entrega tiene su propio commit (el `README.md` con el que lo inicializaste), que tu copia local desconoce. Los dos historiales no comparten ningún ancestro común (*unrelated histories*). |
| **3.4**  | **Descarga el historial del repositorio de entrega sin fusionarlo todavía:** `git fetch origin`.                                                                                                                                                                                                                                                                                     | Ahora tu repositorio local conoce el commit remoto, aunque tu directorio de trabajo no ha cambiado.                                                                                          |
| **3.5**  | **Fusiona explícitamente los dos historiales:** `git merge origin/main --allow-unrelated-histories`. Como ambos `README.md` tienen contenido distinto, **se producirá un conflicto**.                                                                                                                                                                                              | `--allow-unrelated-histories` es obligatorio aquí: por defecto Git no fusiona historiales sin ancestro común, precisamente para evitar mezclar proyectos por error.                          |
| **3.6**  | **Resuelve el conflicto** en `README.md` (decide qué contenido conservar, o combina ambos), elimina los marcadores de conflicto, y finaliza la fusión: `git add README.md` y `git commit` (acepta el mensaje de fusión por defecto).                                                                                                                                               | El *commit* de fusión une ambos historiales conservando el contenido inicial del repositorio de entrega y tu solución.                                                                       |
| **3.7**  | **Sube ahora la entrega:** `git push origin main`. Esta vez el `push` se completa sin errores.                                                                                                                                                                                                                                                                                       | Al compartir ya un ancestro común (el commit de fusión), Git reconoce el `push` como un avance válido.                                                                                       |
| **3.8**  | **Verifica en GitHub** que el repositorio `entrega-examen-simulacro` contiene ahora tanto el `README.md` original como tu fichero `solucion.txt`.                                                                                                                                                                                                                                    | Confirma que la entrega se ha realizado en el repositorio correcto y con todo el contenido esperado.                                                                                         |
| **3.9**  | **Alternativa (solo cuando el contenido inicial no importa):** si en vez de fusionar hubieras querido descartar directamente el `README.md` inicial del repositorio de entrega, podrías haber usado `git push --force origin main` (o, más seguro, `git push --force-with-lease origin main`) en el paso 3.3, sin necesidad de `fetch` ni `merge`.                                | `--force` **sobrescribe** el contenido remoto por completo: es destructivo y solo debe usarse si tienes claro que quieres perder lo que había. En un examen real, comprueba primero si el repositorio de entrega permite `force push` (puede estar protegido). |

### Reflexión Final sobre el Procedimiento de Entrega

Este procedimiento —clonar, resolver, cambiar el remoto y subir a un repositorio distinto— es exactamente el que se seguirá en la prueba práctica:

1.  **El remoto no es automático:** tras un `clone`, `origin` siempre apunta al repositorio de origen. Cambiarlo con `git remote set-url` es un paso **manual e imprescindible** antes de entregar en otro repositorio.
2.  **Un repositorio de entrega no vacío es habitual:** si se crea desde la interfaz web con un `README.md` por defecto, el primer intento de `push` será rechazado. Saber reconocer ese error y resolverlo con `fetch` + `merge --allow-unrelated-histories` (o, cuando proceda, con `--force`) es una habilidad que puede marcar la diferencia el día del examen.
3.  **Comprobar antes de subir:** ejecutar `git remote -v` justo antes de cualquier `push` de entrega evita el error más grave posible: subir la solución al repositorio equivocado.
