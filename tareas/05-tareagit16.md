### Conceptos Clave a Introducir y Reforzar:

1.  **Issue:** Unidad de seguimiento en GitHub para reportar errores, proponer mejoras o planificar tareas, independiente del código pero vinculable a él.
2.  **Asignación (*Assignee*):** Indica qué persona es responsable de resolver un Issue.
3.  **Label (Etiqueta):** Clasifica los Issues por tipo, prioridad o estado (ej: `bug`, `enhancement`, `prioridad-alta`), facilitando el filtrado.
4.  **Palabras Clave de Cierre:** Términos como `Closes`, `Fixes` o `Resolves` seguidos del número del Issue (`#N`) que, incluidos en un mensaje de commit, cierran automáticamente ese Issue al fusionarse o subirse a la rama principal.

### Fase 1: Creación de Issues y Asignación

| **Paso** | **Descripción y Comandos**                                                                                                                                                                                                                                                                                                                                                                                          | **Concepto de Git/GitHub**                                                                     |
| :------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| **1.1**  | **Prepara el proyecto:** crea el directorio `gestor-tareas-issues`, inicialízalo (`git init`), crea `README.md` (`# Gestor de Tareas`) y `index.html` con una estructura básica que **contenga un error intencionado**: el título dentro del `<h1>` no coincide con el proyecto (ej: `<h1>Bienvenido a mi Blog</h1>` en vez de `<h1>Gestor de Tareas</h1>`). Añade y confirma: `git commit -m "feat: Estructura inicial del proyecto"`.                                                                    | Punto de partida sobre el que se reportarán incidencias reales.                                 |
| **1.2**  | **Crea el repositorio remoto y sube el proyecto:** `gh repo create gestor-tareas-issues --public --source=. --push` (o crea el repositorio en la web y usa `git remote add origin <URL>` seguido de `git push -u origin main`).                                                                                                                                                                                     | Los Issues viven en el repositorio remoto de GitHub, no en tu copia local.                      |
| **1.3**  | **Crea tu primer Issue** describiendo el error del título: título `"Bug: el título de la página no coincide con el proyecto"` y una descripción clara de dónde está el error (`index.html`, etiqueta `<h1>`). **Opción Web:** pestaña *Issues* → *New issue*. **Opción CLI:** `gh issue create --title "Bug: el título de la página no coincide con el proyecto" --body "El <h1> de index.html muestra 'Bienvenido a mi Blog' en lugar de 'Gestor de Tareas'."` | El Issue documenta el problema de forma independiente al código, con su propio número (`#1`).   |
| **1.4**  | **Asígnate el Issue a ti mismo:** en la web, panel derecho → *Assignees* → tu usuario. **Alternativa CLI:** `gh issue edit 1 --add-assignee @me`.                                                                                                                                                                                                                                                                    | La asignación deja constancia de quién es responsable de resolver la incidencia.                |
| **1.5**  | **Crea dos Issues adicionales**, uno de tipo mejora (ej: `"Añadir listado de tareas pendientes en index.html"`) y otro de documentación (ej: `"Documentar la estructura de index.html en el README"`), y **asígnatelos también a ti mismo** siguiendo el mismo procedimiento.                                                                                                                                     | Practicar la creación de distintos tipos de incidencia: *bug*, *feature* y *documentación*.      |
| **1.6**  | **Lista todos los Issues abiertos** y comprueba que aparecen los tres, asignados a tu usuario: `gh issue list` o la pestaña *Issues* en la web.                                                                                                                                                                                                                                                                      | `gh issue list` muestra de un vistazo el estado, número y asignación de las incidencias.         |

### Fase 2: Creación y Asignación de Labels

| **Paso** | **Descripción y Comandos**                                                                                                                                                                                                                                     | **Concepto de Git/GitHub**                                                                                 |
| :------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **2.1**  | **Consulta los labels por defecto** que trae todo repositorio de GitHub: `gh label list` (o pestaña *Issues* → *Labels* en la web). Deberías ver `bug`, `enhancement`, `documentation`, entre otros.                                                          | GitHub crea un conjunto de labels estándar automáticamente al crear el repositorio.                          |
| **2.2**  | **Crea un label personalizado** para marcar prioridad: `gh label create "prioridad-alta" --color FF0000 --description "Incidencia que afecta a la primera impresión del proyecto"`. **Alternativa Web:** botón *New label* en la pestaña *Labels*.             | Los labels personalizados permiten adaptar la clasificación a las necesidades del equipo.                     |
| **2.3**  | **Aplica los labels existentes y el nuevo** a los tres Issues creados: el del título incorrecto debe llevar `bug` y `prioridad-alta`; el del listado de tareas, `enhancement`; el de documentación, `documentation`. **Web:** panel derecho del Issue → *Labels*. **CLI:** `gh issue edit 1 --add-label bug,prioridad-alta`. | Un Issue puede tener **varios** labels a la vez.                                                              |
| **2.4**  | **Filtra los Issues por label** para comprobar la clasificación: `gh issue list --label bug` y `gh issue list --label prioridad-alta`.                                                                                                                          | Los labels son la base para filtrar y priorizar el trabajo en repositorios con muchas incidencias abiertas.  |

### Fase 3: Cierre de Issues mediante Commits

| **Paso** | **Descripción y Comandos**                                                                                                                                                                                                                                                                              | **Concepto de Git/GitHub**                                                                                                                                             |
| :------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **3.1**  | **Corrige el error** en `index.html`: cambia el texto del `<h1>` a `Gestor de Tareas`.                                                                                                                                                                                                                   | Cambio real en el código que resuelve la incidencia reportada en el Issue `#1`.                                                                                        |
| **3.2**  | **Confirma el cambio usando una palabra clave de cierre y el número del Issue:** `git add index.html` y `git commit -m "fix: Corregir título de la página (Closes #1)"`.                                                                                                                                | Palabras válidas: `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, siempre seguidas de `#` y el número del Issue.               |
| **3.3**  | **Sube el commit a la rama principal:** `git push origin main`.                                                                                                                                                                                                                                          | El cierre automático solo ocurre cuando el commit llega a la **rama por defecto** del repositorio (directamente o mediante un Pull Request fusionado).                |
| **3.4**  | **Verifica en GitHub** que el Issue `#1` aparece como **cerrado** automáticamente, y que en su historial se referencia el commit que lo cerró: pestaña *Issues* → *Closed*, o `gh issue view 1`.                                                                                                        | El commit y el Issue quedan enlazados de forma permanente y trazable, sin necesidad de cerrarlo a mano.                                                                |
| **3.5**  | **Implementa la mejora del Issue de `enhancement`:** añade a `index.html` una lista `<ul>` con dos o tres `<li>` de tareas de ejemplo. Confirma con un mensaje que también la cierre, referenciando su número (ej: `git commit -m "feat: Añadir listado de tareas (Fixes #2)"`) y súbelo con `git push origin main`. | El mismo mecanismo funciona para cualquier tipo de Issue, no solo para *bugs*.                                                                                         |
| **3.6**  | **Cierra manualmente el Issue de documentación** sin usar un commit, para practicar la alternativa: actualiza el `README.md` explicando la estructura de `index.html`, confirma el cambio con un mensaje normal (sin palabra clave) y cierra el Issue a mano: `gh issue close 3 --comment "Documentación añadida en el README"`. | No todos los Issues se cierran desde un commit; el cierre manual sigue siendo necesario para tareas que no corresponden a un cambio de código concreto.               |
| **3.7**  | **Comprueba el listado final:** `gh issue list --state all`. Los tres Issues deben aparecer como cerrados (*closed*), dos de ellos vinculados a sus respectivos commits.                                                                                                                                 | Vista de conjunto del ciclo de vida completo de las incidencias: creación, asignación, etiquetado y cierre.                                                            |

### Reflexión Final sobre el Seguimiento de Incidencias

Los Issues, combinados con los labels y el cierre automático desde commits, convierten a GitHub en algo más que un simple almacén de código:

1.  **Trazabilidad:** Cada cambio relevante puede vincularse a la incidencia que lo motivó, permitiendo reconstruir el "por qué" de una modificación mucho después de haberla hecho.
2.  **Organización del Trabajo:** La asignación y el etiquetado permiten repartir tareas y priorizarlas sin salir de la plataforma.
3.  **Automatización:** Cerrar Issues desde el propio mensaje de commit evita el trabajo manual y asegura que el estado de la incidencia siempre esté sincronizado con el código que la resuelve.
